# Loop

Многопользовательская аркадная гонка на картах с собственным сеттингом, персонажами и визуальным стилем. Учебный проект по дисциплине «Проектирование и разработка многопользовательских игр и клиент-серверных систем».

## 1. Проект и топология

**Проект:** «Loop» — 3D-аркада на картах для 4–12 игроков одновременно в одной гонке. Игроки выбирают трассу и персонажа, соревнуются на 3 кругах, используют предметы-бонусы (ускорение, снаряды, щиты, бананы-мины), которые подбираются в случайных боксах на трассе.

**Выбранная топология: клиент-серверная, модель Listen Server (хост-авторитетный сервер) с возможностью перехода на выделенный (dedicated) сервер.**

Один из клиентов (хост лобби) одновременно выполняет роль авторитетного игрового сервера: принимает ввод от всех клиентов, симулирует физику карта, столкновения, срабатывание предметов, определяет положение на трассе и рассылает снапшоты состояния остальным клиентам. Клиенты выполняют локальное предсказание движения (client-side prediction) и интерполяцию/экстраполяцию чужих карт, чтобы сгладить сетевые задержки.

Архитектура спроектирована так, чтобы при росте нагрузки (публичный матчмейкинг, турниры, защита от читеров) хост-часть можно было вынести на выделенный сервер в облаке без изменения сетевого протокола — меняется только то, где физически исполняется авторитетная логика (на машине игрока или на сервере), сама модель "клиент отправляет ввод — сервер отправляет состояние" остаётся прежней.

Альтернативы, которые были рассмотрены и отклонены:

| Топология | Почему не выбрана |
|---|---|
| Чистый P2P (mesh, каждый с каждым) | Сложная синхронизация состояния между всеми парами клиентов, легко читерить (нет единого источника истины), трафик растёт квадратично от числа игроков |
| Выделенный сервер с самого старта | Избыточен для учебного/пет-проекта на старте — требует постоянного бюджета на хостинг ещё до того, как игра набрала аудиторию |
| Relay-сервер (только пересылка пакетов, без логики) | Не решает проблему авторитетности — читер всё равно может подделывать своё состояние, т.к. сервер не проверяет физику |

## 2. Обоснование топологии

### Число игроков
Гонка рассчитана на 4–12 игроков в одной сессии — стандартный диапазон для аркадных карт-рейсеров жанра. Это небольшое количество одновременных соединений, с которым один клиент-хост справляется без специализированного серверного железа: обработка ввода и физики 12 карт — не ресурсоёмкая задача даже на обычном игровом ПК или консоли игрока.

### Нагрузка
Состояние гонки компактно: позиция, вращение, скорость, текущий предмет и circuit-progress каждого карта. При частоте синхронизации ~20–30 снапшотов/сек и 12 игроках исходящий трафик хоста составляет порядка нескольких десятков КБ/с — это укладывается в возможности обычного домашнего интернет-канала, что и делает listen-server жизнеспособным без дата-центра. При переходе на публичный релиз с сотнями одновременных лобби нагрузка линейно размножается по количеству независимых гонок, а не растёт внутри одной гонки, поэтому масштабирование делается горизонтально — просто больше инстансов игровых сессий на выделенных серверах, что укладывается в ту же клиент-серверную модель.

### Задержки (latency)
Гоночный жанр чувствителен к задержке ввода (руление, ускорение, использование предметов должны ощущаться мгновенно), но, в отличие от шутеров, не требует латентности <30 мс — приемлемый порог 80–150 мс благодаря:
- **client-side prediction** — локальный клиент сразу применяет собственный ввод, не дожидаясь ответа сервера;
- **интерполяции чужих карт** — сглаживание позиции соперников между снапшотами;
- **серверной реконсиляции** — коррекция расхождений без резких "телепортов".

Модель listen server дополнительно снижает задержку для большинства матчей: хост, как правило, находится в том же регионе/стране, что и остальные игроки (матчмейкинг по регионам), поэтому RTT до хоста меньше, чем до удалённого дата-центра на другом континенте — в отличие от ситуации, когда единственный дешёвый dedicated-сервер стоит в одном фиксированном регионе.

### Бюджет
Проект учебный/пет-разработка без изначального бюджета на инфраструктуру. Listen server не требует аренды серверов вообще — единственная инфраструктурная статья расходов на старте — это бесплатный или почти бесплатный relay/matchmaking-сервис для NAT punchthrough и подбора лобби (например, бесплатные тиры Photon, Steam Relay, или self-hosted signaling-сервер на минимальном VPS за $3–5/мес). Полноценный выделенный игровой сервер (аренда VPS под геймсервер, масштабирование, DDoS-защита) откладывается до момента, когда у игры появится аудитория и, соответственно, источник монетизации/бюджета — архитектура клиент-сервер это позволяет сделать позже без переписывания сетевого кода.

### Итог
Для 4–12 игроков в гонке, с некритичной к сверхнизкой задержке аркадной физикой и нулевым стартовым бюджетом, клиент-серверная модель с авторитетным listen-server-хостом даёт баланс: единый источник истины (защита от читов лучше, чем в P2P), приемлемая задержка за счёт региональности хоста и client-side prediction, и нулевые расходы на старте — с чётким путём миграции на выделенные серверы при росте проекта.
