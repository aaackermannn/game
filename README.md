# Loop

Многопользовательская аркадная гонка на картах с собственным сеттингом, персонажами и визуальным стилем. Учебный проект по дисциплине «Проектирование и разработка многопользовательских игр и клиент-серверных систем».

## 1. Проект и топология

**Проект:** «Loop» — 3D-аркада на картах для 4–12 игроков одновременно в одной гонке. Игроки выбирают трассу и персонажа, соревнуются на 3 кругах, используют предметы-бонусы (ускорение, снаряды, щиты, бананы-мины), которые подбираются в случайных боксах на трассе.

**Выбранная топология: клиент-серверная, модель Dedicated Server (выделенный игровой сервер).**

Сервер работает отдельным процессом без игрового клиента и графики. Все игроки подключаются к нему по адресу и UDP-порту; ни один клиент не совмещает роль игрока и игрового сервера. При размещении на отдельной машине работа сервера не зависит от того, кто создал лобби и остаётся ли этот игрок в игре.

В целевой версии сервер принимает ввод игроков, симулирует движение карт, столкновения и предметы, определяет прогресс гонки и рассылает состояние участникам. Клиенты отображают гонку; локальное предсказание движения (client-side prediction), интерполяция чужих карт и согласование с сервером планируются для сглаживания задержек.

В практической №1 уже реализованы отдельные процессы `loop_server` и `loop_client`, подключение по адресу и UDP-протокол. Это основа dedicated-модели, но пока не полная симуляция гонки: сервер принимает координаты `MOVEMENT` без проверки, имитирует попадания и отвечает только отправителю. Проверка движения, серверный игровой цикл, рассылка состояния всем участникам и обработка отключений ещё предстоят.

Альтернативы, которые были рассмотрены и отклонены:

| Топология | Почему не выбрана |
|---|---|
| Чистый P2P (mesh, каждый с каждым) | Сложная синхронизация состояния между всеми парами клиентов, легко читерить (нет единого источника истины), трафик растёт квадратично от числа игроков |
| Listen Server (сервер внутри клиента-хоста) | Сессия зависит от машины и соединения игрока-хоста; его выход требует завершения сессии или переноса серверной роли. Для текущих отдельных серверного и клиентского приложений dedicated проще |
| Relay-сервер (только пересылка пакетов, без логики) | Не решает проблему авторитетности — читер всё равно может подделывать своё состояние, т.к. сервер не проверяет физику |

## 2. Обоснование топологии

### Число игроков
Гонка рассчитана на 4–12 игроков в одной сессии. На старте планируется один серверный процесс на одну гонку. Сервер не выполняет рендеринг, а его нагрузка зависит от сложности симуляции и частоты обновлений; подходящие ресурсы нужно определить нагрузочным тестированием.

### Нагрузка
Планируемое состояние гонки включает позицию, вращение, скорость, текущий предмет и прогресс каждого карта. Целевая частота снапшотов — 20–30 в секунду; текущая практическая пока использует ответы на запросы. Исходящий трафик сервера определяется размером снапшота × частотой отправки × числом получателей, поэтому его нужно измерять после реализации рассылки. При росте числа независимых гонок можно запускать дополнительные серверные процессы; автоматическое распределение сессий пока не реализовано.

### Задержки (latency)
Гоночный жанр чувствителен к задержке ввода: руление, ускорение и использование предметов должны ощущаться мгновенно. Для целевой версии планируются:
- **client-side prediction** — локальный клиент сразу применяет собственный ввод, не дожидаясь ответа сервера;
- **интерполяции чужих карт** — сглаживание позиции соперников между снапшотами;
- **серверной реконсиляции** — коррекция расхождений без резких "телепортов".

Выделенный сервер следует размещать ближе к игрокам, а при подборе учитывать задержку до доступных серверов. Dedicated сам по себе не гарантирует меньший ping: результат зависит от региона размещения и сетевых маршрутов. Допустимую задержку нужно проверить на игровом прототипе.

### Бюджет
Для разработки и защиты практической dedicated-сервер можно запускать на том же ПК, что и клиенты, либо на отдельной машине в локальной сети — аренда не требуется. Здесь «выделенный» означает отдельную серверную программу, а не обязательную покупку физического сервера. Для постоянной игры через интернет понадобится доступная машина, например VPS, с разрешённым входящим UDP-трафиком на игровом порту; стоимость зависит от выбранного размещения и нагрузки. За запуск, обновления и доступность сервера отвечает разработчик или администратор.

При прямом подключении к публичному серверу клиентам не требуется принимать входящие соединения от других игроков. Если сервер размещён дома за NAT, на его стороне понадобятся публичная доступность и настройка перенаправления UDP-порта; один лишь запуск отдельного процесса эту задачу не решает.

### Итог
Dedicated Server соответствует существующему разделению `GameServer`/`GameClient`, упрощает совместное тестирование и позволяет независимо размещать сервер. Все клиенты обращаются к одному серверу, который в целевой версии проверяет действия и хранит авторитетное состояние. Компромисс — необходимость поддерживать сервер и оплачивать размещение при использовании платной инфраструктуры. Сама топология не заменяет проверку клиентского ввода и обработку потерь связи.

### Локальный запуск

После сборки CMake в Visual Studio запустить сервер в одном терминале, а каждого клиента — в отдельном:

```powershell
.\build\Debug\loop_server.exe 27015
```

```powershell
.\build\Debug\loop_client.exe 127.0.0.1 27015 1.0 player1 pass123
```

```powershell
.\build\Debug\loop_client.exe 127.0.0.1 27015 1.0 player2 pass456
```

При размещении сервера на другой машине заменить `127.0.0.1` её доступным IPv4-адресом или DNS-именем. Порт по умолчанию — `27015/UDP`. Для других вариантов сборки см. [инструкцию](docs/pr1-udp-protocol.md#7-сборка-и-запуск).

## Практические работы

- **№4 — Client-Side Prediction и Server Reconciliation.** В Godot-клиенте (`kart/`) режим **NET LAB**: listen server + клиенты по ENet, сервер-авторитет, детерминированное движение `NetSim.step()`, сохранённые ходы, коррекция и повторное проигрывание ввода, рывок с серверной проверкой кулдауна, эмулятор `NetEmulation.*`. Без предсказания рывок виден через ~293 мс (100 мс в каждую сторону), с предсказанием — в том же кадре. [Отчёт](docs/Prediction_Implementation.md) · [Матрица тестов](docs/Prediction_Test_Matrix.md) · [Видео и скриншоты](docs/media/) · код [`kart/scripts/net/`](kart/scripts/net/) · [Объяснение простыми словами (docx)](Защита_ПР4/ПР4_объяснение_для_первоклассника.docx).

- **№3 — надёжная доставка критичных команд.** UDP-стенд из ПР №2 подтверждает `SHOOT` и повторяет его при адаптивном тайм-ауте. [Отчёт и эксперимент](pr2-latency-template/docs/Reliability_Protocol.md) · [Материалы для защиты](Защита_ПР3/Защита_практической_работы_3.docx) · [Разбор реализации по ТЗ](Защита_ПР3/Разбор_реализации_ПР3_по_ТЗ.docx).

- **№1 — UDP-протокол и архитектура.** Консольные UDP-сервер и клиент на C++ (Berkeley Sockets/Winsock, адрес резолвится через `getaddrinfo()`), ООП-структура (`UdpSocket`, `GameServer`, `GameClient`), команды `MOVEMENT`/`SHOOT`/`AUTH`, заголовок с sequence-номером и CRC32-checksum, логирование на сервере. Код: [`net/`](net/), [`server/`](server/), [`client/`](client/). Спецификация протокола: [docs/pr1-udp-protocol.md](docs/pr1-udp-protocol.md). Отчёт о выполнении по шагам: [docs/pr1.md](docs/pr1.md).
- **№2 — телеметрия UDP.** Отдельный проект [`pr2-latency-template/`](pr2-latency-template/README.md): PING/PONG, модули protocol/telemetry/transport, RTT/SRTT/jitter/loss, проверка ошибочных и поздних ответов, Catch2 и UDP-интеграция. Проведены 6 серий по 100 PING; исходные CSV, параметры и графики — в [отчёте](pr2-latency-template/docs/Latency_Report.md). Формат ПР №2 отделён от ПР №1.
