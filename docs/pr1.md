# Практическая работа №1 — отчёт о выполнении

Спецификация протокола и архитектурные решения оформлены отдельно в [pr1-udp-protocol.md](pr1-udp-protocol.md) — этот файл описывает **последовательность шагов**, которыми практическая была выполнена.

## Что требовалось

Консольные UDP-сервер и UDP-клиент (C++ или C#) с обменом пакетами вида «заголовок (тип команды, sequence, размер данных) + payload», минимум двумя командами (`MOVEMENT`, `SHOOT`), логированием на сервере и периодической отправкой на клиенте. Дополнительно — CRC32-checksum в заголовке и простая авторизация по логину/паролю.

## Шаг 1. Выбор языка

Рассмотрели C++ (системные Berkeley Sockets/Winsock) и C# (`UdpClient`). Выбран **C++** — ближе к методичке (Beej's Guide и оба примера кода в задании написаны на C++), даёт полный контроль над байтами заголовка через `#pragma pack`, и совпадает с языком, на котором, вероятно, будет вестись остальной сетевой код проекта.

## Шаг 2. Проверка окружения сборки

CMake и g++ в системе не установлены, но обнаружен MSVC-тулчейн (Visual Studio Community, `VC\Tools\MSVC\14.51.36231`). Сборка и все проверки в этой работе выполнялись через `cl.exe` из Developer Command Prompt (`vcvars64.bat`); `CMakeLists.txt` написан дополнительно для кроссплатформенной сборки (Linux/macOS через CMake+g++/clang++, см. [pr1-udp-protocol.md, §7](pr1-udp-protocol.md#7-сборка-и-запуск)), но на этой машине не проверялся, так как CMake не установлен.

## Шаг 3. Проектирование протокола

До кода — спроектирован формат пакета: заголовок 12 байт (`magic`, `type`, `sequence`, `payloadSize`, `checksum`), 7 типов команд (`AUTH`, `MOVEMENT`, `SHOOT` от клиента; `AUTH_RESULT`, `STATE_UPDATE`, `SHOOT_RESULT`, `ERROR_RESP` от сервера) и структуры payload под каждый тип. Полное описание — [pr1-udp-protocol.md, §2](pr1-udp-protocol.md#2-формат-пакета).

## Шаг 4. Общий код протокола (`net/`)

- [`net/protocol.h`](../net/protocol.h) — заголовок, типы команд, payload-структуры, `buildPacket()`/`parsePacket()` с переводом целочисленных полей в сетевой порядок байт (`htons`/`htonl`).
- [`net/crc32.h`](../net/crc32.h) — табличная CRC32 (полином `0xEDB88320`, как в zip/PNG/Ethernet).
- [`net/net_compat.h`](../net/net_compat.h) — кроссплатформенная обёртка: `NetGuard` (WSAStartup/WSACleanup на Windows), общие типы сокета, таймаут приёма.

## Шаг 5. Первая версия сервера и клиента

Написаны `server/server.cpp` и `client/client.cpp` — процедурный стиль, всё в одном `main()` на файл: ручное заполнение `sockaddr_in`, цикл `socket → bind → recvfrom/sendto` на сервере, периодическая отправка `MOVEMENT`/`SHOOT` на клиенте с таймаутом на приём ответа.

## Шаг 6. Сборка и первый сквозной тест

Собрано через `cl /std:c++17 /EHsc /W4 ... /link ws2_32.lib` — без ошибок, с одним предупреждением (недостижимый код после `for(;;)`), которое затем убрано. Сервер и клиент запущены на `127.0.0.1`: проверен полный цикл `AUTH → MOVEMENT/STATE_UPDATE → SHOOT/SHOOT_RESULT` за ~20 тиков, лог сервера (`server.log`) сверен построчно — все команды и таймстампы на месте.

## Шаг 7. Тест негативного сценария

Отдельным запуском проверена авторизация с неверными логином/паролем: сервер отвечает `AUTH_RESULT{success=0}`, логирует `FAIL`, дальнейшие `MOVEMENT` от этого клиента помечаются в логе как `(не авторизован)`, но не блокируются — осознанное решение, объяснено в [pr1-udp-protocol.md, §5](pr1-udp-protocol.md#5-авторизация-доп-задание).

## Шаг 10. Сверка с методичкой и примерами кода

По запросу проверено, насколько реализация соответствует сопровождающим материалам задания (`WebFetch` по трём источникам):

- **Beej's Guide, §6.3 (UDP)** — тот же набор вызовов (`socket/bind/recvfrom` на сервере, `socket/sendto` на клиенте), но гайд рекомендует резолвить адрес через `getaddrinfo()`, а не вручную через `sockaddr_in`.
- **SAIRISAN123/UDP_Server.cpp** — тот же скелет сервера (`socket → bind → while(true){recvfrom; sendto}`), ручное заполнение `sockaddr_in`, без `getaddrinfo()` — совпадает с шагом 5.
- **naoko-portfolio/tcp-udp-socket-programming-cpp** — проверка через GitHub API (дерево файлов) показала, что в репозитории **только `README.md`** со скриншотами кода; реальных `.cpp`/`.h`-файлов нет, воспроизвести структуру буквально было неоткуда.
- **stephan-brumme CRC32** — тот же полином и инициализация/финализация (`0xFFFFFFFF`/`~crc`), что уже было реализовано в шаге 4.

## Шаг 11. Рефакторинг: `getaddrinfo()` и ООП

По итогам сверки и по прямому запросу — код переписан:

- Добавлен класс [`UdpSocket`](../net/udp_socket.h) ([.cpp](../net/udp_socket.cpp)) — RAII-обёртка над сокетом, адрес резолвится через `getaddrinfo()` (как в канонических `listener.c`/`talker.c` из Beej's Guide) вместо ручного `sockaddr_in`.
- Серверная логика вынесена в класс [`GameServer`](../server/game_server.h) ([.cpp](../server/game_server.cpp)) с приватными методами-обработчиками (`handleAuth`, `handleMovement`, `handleShoot`, `handleUnknown`, `handleBadChecksum`) и классом `Logger`; `server/server.cpp` сведён к точке входа.
- Клиентская логика вынесена в класс [`GameClient`](../client/game_client.h) ([.cpp](../client/game_client.cpp)); `client/client.cpp` сведён к точке входа.
- `net_compat.h` дополнен алиасом `socklen_compat` (различие `int`/`socklen_t` между Winsock и POSIX) и `<netdb.h>` для POSIX.
- `CMakeLists.txt` обновлён под новый список исходников.

ООП-структура спроектирована самостоятельно (см. шаг 10 про `naoko-portfolio`), не скопирована откуда-либо.

## Шаг 12. Повторная сборка и повторный сквозной тест

Пересобрано через `cl` — чисто, без предупреждений. Повторены оба сценария из шагов 6–7 (успешная и неуспешная авторизация, `MOVEMENT`/`SHOOT` roundtrip) — поведение и формат вывода идентичны версии до рефакторинга.
