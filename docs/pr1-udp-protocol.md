# Практическая работа №1 — UDP-протокол и архитектура

Реализация: [`net/`](../net/) (общий протокол и сокет), [`server/`](../server/) (класс `GameServer`), [`client/`](../client/) (класс `GameClient`).

### Соответствие методичке и примерам

- **Сокеты и порядок вызовов** — Berkeley Sockets/Winsock напрямую, без сторонних библиотек, как требует задание.
- **Резолвинг адреса — через `getaddrinfo()`**, как в канонических `listener.c`/`talker.c` из [Beej's Guide, §6.3](https://beej.us/guide/bgnet/html/#datagram) (см. [`net/udp_socket.cpp`](../net/udp_socket.cpp)), а не вручную через `sockaddr_in` — это официально рекомендованный гайдом портируемый способ.
- **Структура кода — ООП**: `UdpSocket` (RAII-обёртка сокета) в `net/`, `GameServer`/`GameClient` — классы с приватными методами-обработчиками команд, вместо одной процедуры `main()`.
- Из двух примеров кода, данных в задании, реально удалось свериться только с [SAIRISAN123/UDP_Server.cpp](https://github.com/SAIRISAN123/Networking_Template_Code/blob/main/UDP_C%2B%2B/UDP_Server.cpp) — простой echo-сервер тем же набором вызовов (`socket → bind → recvfrom/sendto` в цикле). Репозиторий [naoko-portfolio/tcp-udp-socket-programming-cpp](https://github.com/naoko-portfolio/tcp-udp-socket-programming-cpp), указанный вторым примером, при проверке (GitHub API, дерево файлов) содержит только `README.md` со скриншотами кода — исходных `.cpp`/`.h` файлов в нём нет, поэтому воспроизвести оттуда что-либо буквально было невозможно; структура классов ниже спроектирована самостоятельно.

## 1. Архитектура

### Топология

Полное обоснование топологии проекта — в [README](../README.md#1-проект-и-топология). Кратко: боевая модель — **Listen Server** (клиент-хост одновременно исполняет роль авторитетного сервера).

Для этой практической сервер и клиент реализованы как два отдельных процесса — так того требует задание, и так удобнее проверять протокол независимо от игрового кода. Это не противоречит выбранной топологии: протокол и класс `GameServer` написаны так, что не зависят от того, где физически исполняется серверная роль — как отдельный процесс (как сейчас) или как поток внутри процесса клиента-хоста (боевой режим Listen Server). Сетевой протокол (заголовок, типы команд, сериализация) одинаков в обоих случаях.

### Распределение обязанностей

**Сервер (`GameServer`, [`server/game_server.cpp`](../server/game_server.cpp)) отвечает за:**
- приём UDP-пакетов от всех клиентов на одном порту (`bind` + `recvfrom` в цикле);
- разбор заголовка, проверку magic-байта и контрольной суммы (CRC32);
- хранение авторитетного состояния каждого клиента (позиция, здоровье, статус авторизации) в таблице по адресу `ip:port`;
- обработку команд `MOVEMENT` / `SHOOT` / `AUTH` и формирование ответа;
- проверку логина/пароля по захардкоженному списку (доп. задание);
- логирование всех принятых команд в консоль и файл `server.log`.

**Клиент (`GameClient`, [`client/game_client.cpp`](../client/game_client.cpp)) отвечает за:**
- отправку `AUTH` перед началом игровой сессии;
- периодическую (раз в `interval` секунд) отправку `MOVEMENT` и, раз в 3 тика, `SHOOT`;
- присвоение возрастающего порядкового номера (`sequence`) каждому исходящему пакету;
- приём и разбор ответа сервера с таймаутом (1.5 c), чтобы не блокироваться навечно при недоступном сервере;
- вывод результата в консоль.

Это соответствует общей идее клиент-серверной модели: **клиент никогда не считается источником истины** — он только отправляет намерения (`MOVEMENT` как желаемая позиция, `SHOOT` как факт выстрела), а сервер утверждает и рассылает актуальное состояние (`STATE_UPDATE`, `SHOOT_RESULT`). В боевой версии игры это же разделение защищает от читов: клиент не может напрямую подделать здоровье соперника или исход попадания.

## 2. Формат пакета

Все структуры упакованы (`#pragma pack(push, 1)`) — без выравнивания, чтобы бинарный layout был одинаков независимо от компилятора.

### Заголовок — 12 байт, одинаков для всех типов пакетов

| Поле | Тип | Байт | Порядок байт | Описание |
|---|---|---|---|---|
| `magic` | `uint8_t` | 1 | — | Сигнатура протокола, всегда `0xA5`. Пакеты с другим значением отбрасываются как чужеродный трафик |
| `type` | `uint8_t` | 1 | — | Код команды, см. таблицу типов ниже |
| `sequence` | `uint32_t` | 4 | network (big-endian) | Порядковый номер пакета отправителя |
| `payloadSize` | `uint16_t` | 2 | network (big-endian) | Размер полезной нагрузки, идущей сразу за заголовком |
| `checksum` | `uint32_t` | 4 | network (big-endian) | CRC32 от payload; `0`, если целостность не проверяется |

Многобайтовые целочисленные поля заголовка переводятся в сетевой порядок байт через `htons`/`htonl` при сборке пакета и обратно через `ntohs`/`ntohl` при разборе — см. `proto::buildPacket` / `proto::parsePacket` в [`net/protocol.h`](../net/protocol.h).

Поля полезной нагрузки (включая `float`) передаются как есть, без перестановки байт — осознанное упрощение, рассчитанное на little-endian хосты по обе стороны соединения (x86/x64/ARM — подавляющее большинство настольных, серверных и мобильных платформ). Для полностью кроссплатформенного протокола (в т.ч. big-endian-хосты) потребовалась бы явная сериализация каждого float-поля, что выходит за рамки практической.

### Типы пакетов

| Значение | Имя | Направление | Payload |
|---|---|---|---|
| 1 | `AUTH` | клиент → сервер | `AuthPayload` |
| 2 | `MOVEMENT` | клиент → сервер | `MovementPayload` |
| 3 | `SHOOT` | клиент → сервер | `ShootPayload` |
| 10 | `AUTH_RESULT` | сервер → клиент | `AuthResultPayload` |
| 11 | `STATE_UPDATE` | сервер → клиент | `StateUpdatePayload` |
| 12 | `SHOOT_RESULT` | сервер → клиент | `ShootResultPayload` |
| 13 | `ERROR_RESP` | сервер → клиент | `ErrorPayload` |

### Payload'ы

```cpp
struct AuthPayload {        // клиент -> сервер, 64 байта
    char username[32];
    char password[32];
};

struct MovementPayload {    // клиент -> сервер, 8 байт
    float x;
    float y;
};

struct ShootPayload {       // клиент -> сервер, 12 байт
    float dirX;
    float dirY;
    uint32_t weaponId;
};

struct AuthResultPayload {  // сервер -> клиент, 65 байт
    uint8_t success;        // 0/1
    char message[64];
};

struct StateUpdatePayload { // сервер -> клиент, 20 байт
    uint32_t clientId;
    float x;
    float y;
    uint32_t health;
    uint32_t ackSequence;   // sequence обработанного запроса клиента
};

struct ShootResultPayload { // сервер -> клиент, 9 байт
    uint8_t hit;             // 0/1
    uint32_t targetId;       // 0, если целей не было
    uint32_t ackSequence;
};

struct ErrorPayload {       // сервер -> клиент, 64 байта
    char message[64];
};
```

## 3. Порядковые номера (sequence)

Клиент хранит один счётчик `sequence`, увеличивая его перед отправкой **каждого** пакета (включая `AUTH`) — единая монотонно растущая последовательность на клиента, не отдельная для каждого типа команд. Сервер не хранит номер сам по себе, а возвращает полученный `sequence` обратно в поле `ackSequence` соответствующего ответа — это позволяет клиенту сопоставить ответ с конкретным запросом (полезно при потере пакетов или переупорядочивании, свойственных UDP).

## 4. Контрольная сумма (доп. задание)

CRC32 (полином `0xEDB88320`, как в zip/PNG/Ethernet) считается только от **payload**, не от заголовка — реализация в [`net/crc32.h`](../net/crc32.h). При сборке пакета отправитель кладёт значение в заголовок; получатель пересчитывает CRC32 от полученного payload и сравнивает. При несовпадении сервер логирует инцидент и отвечает `ERROR_RESP`, не обрабатывая команду — это защищает от повреждённых в сети или намеренно подделанных пакетов.

## 5. Авторизация (доп. задание)

Список логин/пароль захардкожен на сервере (`kCredentials` в `server/game_server.cpp`) — `player1/pass123`, `player2/pass456`, `admin/admin123`. Клиент отправляет `AUTH` первым пакетом сессии; сервер помечает адрес клиента как авторизованный/неавторизованный и логирует попытку. **Успешная авторизация не блокирует дальнейшие команды** — `MOVEMENT`/`SHOOT` от неавторизованного клиента всё равно обрабатываются, но помечаются в логе сервера как `(не авторизован)`. Такое мягкое поведение выбрано намеренно для практической: демонстрирует механизм проверки учётных данных, не усложняя тестирование остальных команд отдельным обязательным хендшейком. В боевой версии (после интеграции с реальным аккаунтом игрока) это переключается в строгий режим — отказ в обработке команд до успешного `AUTH`.

## 6. Логирование

Сервер пишет каждую принятую команду и результат её обработки в двух местах: `stdout` и файл `server.log` (создаётся рядом с исполняемым файлом сервера, дописывается при перезапуске). Формат строки: `[YYYY-MM-DD HH:MM:SS] [ip:port] TYPE поля...`.

## 7. Сборка и запуск

### Через CMake (кроссплатформенно)

```sh
cmake -S . -B build
cmake --build build --config Release
```

Исполняемые файлы появятся как `loop_server` / `loop_client` (или `.exe` на Windows) внутри `build/`.

### Напрямую через компилятор

Windows (MSVC, из Developer Command Prompt):
```bat
cl /std:c++17 /EHsc /O2 /Fe:server\loop_server.exe server\server.cpp server\game_server.cpp net\udp_socket.cpp /link ws2_32.lib
cl /std:c++17 /EHsc /O2 /Fe:client\loop_client.exe client\client.cpp client\game_client.cpp net\udp_socket.cpp /link ws2_32.lib
```

Linux/macOS (g++/clang++):
```sh
g++ -std=c++17 -O2 -o server/loop_server server/server.cpp server/game_server.cpp net/udp_socket.cpp
g++ -std=c++17 -O2 -o client/loop_client client/client.cpp client/game_client.cpp net/udp_socket.cpp
```

### Запуск

```sh
# терминал 1
./server/loop_server 27015

# терминал 2
./client/loop_client 127.0.0.1 27015 1 player1 pass123
#                     host       port interval_sec login password
```

Все параметры клиента опциональны и имеют значения по умолчанию (`127.0.0.1 27015 1.0 player1 pass123`).

## 8. Проверено вручную

- Полный цикл `AUTH → MOVEMENT/STATE_UPDATE → SHOOT/SHOOT_RESULT` на локальном сокете (127.0.0.1) — сервер и клиент обмениваются пакетами каждый тик, ответы приходят с корректным `ackSequence`.
- Неверные логин/пароль: сервер отвечает `AUTH_RESULT{success=0}`, логирует `FAIL`, дальнейшие команды помечаются как неавторизованные, но продолжают обрабатываться.
- Лог сервера (`server.log`) корректно фиксирует все команды с таймстампами.
- Проверка повторена после перехода на `getaddrinfo()` и разбиения на классы `UdpSocket`/`GameServer`/`GameClient` — поведение и формат вывода идентичны варианту на ручном `sockaddr_in`.
