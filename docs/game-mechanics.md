# Игровые механики

Список ключевых механик Loop поверх базового карт-рейсинга (трасса, круги, позиция). Для каждой — геймплейное описание и заметка о сетевых требованиях (кто авторитетен, что нужно синхронизировать), поскольку это напрямую влияет на протокол ([docs/pr1-udp-protocol.md](pr1-udp-protocol.md)) и архитектуру ([README](../README.md#1-проект-и-топология)).

## 1. Лутбоксы с оружием и баффами

На трассе расставлены фиксированные точки лутбоксов (по аналогии с item box). При проезде через box игрок получает один случайный предмет из общего пула — оружие (снаряд, мина) или бафф (ускорение, щит, невидимость). Box после подбора становится пустым и восстанавливается через фиксированное время (например, 5–8 с). У игрока в один момент — один предмет в инвентаре (слот), новый подбор возможен только после использования текущего.

**Сеть:** подбор — авторитетное решение сервера, не клиента. Клиент лишь сообщает «доехал до точки X» (или сервер сам детектит пересечение по присланной позиции), сервер бросает случайный ролл, обновляет состояние box (пусто/полно) и возвращает результат подбора клиенту. Это защищает от читов вида «выбрать себе легендарное оружие на клиенте» и от двойного подбора одного бокса двумя игроками одновременно (race condition решается тем, что сервер — единственный источник истины и обрабатывает пакеты последовательно).

## 2. Энергия, раскиданная по трассе

Помимо лутбоксов — мелкие подбираемые «частицы энергии» вдоль трассы (аналог монет), которых много и они мельче по геймплейному весу. Собранная энергия копится в отдельную шкалу и тратится на активацию усиленной версии текущего предмета или на короткий буст скорости без использования лутбокса. Респавнятся волнами (например, все энергетические точки на круге появляются заново в начале нового круга).

**Сеть:** из-за высокой частоты подбора (десятки точек на трассу) поштучные пакеты на каждую подобранную частицу были бы избыточны — рационально агрегировать: клиент шлёт позицию как обычно (`MOVEMENT`), сервер сам определяет пересечения с точками энергии по серверной копии позиции и включает изменение шкалы энергии в очередной `STATE_UPDATE`, а не создаёт отдельный тип пакета на каждый подбор.

## 3. Матчмейкинг

Подбор игроков в гонку перед стартом — по региону и задержке до доступных серверов (см. обоснование топологии в README) и, опционально, по уровню/рейтингу. Игрок нажимает «Найти игру», встаёт в очередь, при наборе 4–12 игроков формируется лобби и выделяется серверный процесс для гонки.

**Сеть:** в целевой версии матчмейкинг — отдельный сервис, который собирает игроков, выбирает доступный dedicated-сервер и передаёт клиентам его адрес и UDP-порт. Он не участвует в игровой симуляции. Автоматическое выделение серверных процессов и матчмейкинг пока не реализованы; в практической сервер запускается вручную, а его адрес задаётся аргументом клиента.

## 4. Система лобби

Предстартовая комната: список игроков, их выбор карта/персонажа, статус готовности («ready»), владелец лобби может запросить исключение игрока или смену трассы, возможно голосование за трассу. Владелец лобби — обычный клиент с правами управления комнатой; серверную роль он не выполняет. Гонка стартует по правилам сервера: когда все готовы, по таймеру либо по разрешённому запросу владельца.

**Сеть:** dedicated-сервер проверяет права и запросы клиентов, хранит состояние лобби (кто в комнате, кто готов, что выбрано) и рассылает его всем участникам при каждом изменении. Выход владельца не завершает серверный процесс; в целевой версии права управления комнатой передаются другому участнику по серверным правилам. Состояние лобби передаётся поверх того же UDP-соединения отдельно от игровых команд `MOVEMENT`/`SHOOT` (планируемые типы пакетов `LOBBY_STATE`, `PLAYER_READY`, вне рамок PR1, по той же схеме заголовок+payload). Система лобби и передача прав пока не реализованы.

## 5. Лидерборд в игре

Во время гонки — постоянно обновляемая турнирная таблица (позиция по кругам/прогрессу трассы, отставание от лидера в секундах), видимая всем игрокам поверх экрана. После финиша — итоговая таблица и, в перспективе, персистентная статистика игрока (лучшие круги, побед).

**Сеть:** не отдельный канал данных — вычисляется сервером из уже имеющихся `STATE_UPDATE` всех игроков (позиция + прогресс по трассе), сортируется и рассылается как часть общего снапшота состояния гонки. Клиент не может считать себя первым на основании собственных данных — ранжирование только серверное, иначе тривиально подделывается.

## 6. Оружие из лутбоксов и система повреждений

Применение подобранного оружия — то же действие `SHOOT`, уже заложенное в протокол PR1 ([`ShootPayload`](pr1-udp-protocol.md#payloadы)), только с разным эффектом в зависимости от типа предмета: снаряд бьёт по цели по прямой, мина остаётся на трассе и срабатывает при наезде, щит блокирует ближайшее попадание. Попадание не «убивает», а временно ослабляет — сброс скорости, кратковременная потеря управления (spin-out), или, для здоровья/прочности карта — постепенная деградация, влияющая на макс. скорость, восстанавливаемая пит-стопом/временем.

**Сеть:** прямое расширение существующего `SHOOT`/`SHOOT_RESULT` — `weaponId` уже есть в `ShootPayload`, `health` уже есть в `StateUpdatePayload`. Сервер авторитетно решает попадание/промах и эффект (как уже реализовано в `GameServer::handleShoot` для практической №1 — заглушка 50/50 будет заменена на реальную геометрическую проверку траектории снаряда против позиций других карт).

## Все видят происходящие изменения на карте

Сквозное требование поверх всех механик выше: опустевший лутбокс, оставленная на трассе мина, чужой активный щит — должны быть видны **всем** участникам гонки в реальном времени, не только тому, кто вызвал изменение. Это меняет базовую модель обмена пакетами: недостаточно, чтобы сервер отвечал только отправителю (как сейчас `unicast`-ответ в PR1) — при обработке события с видимым эффектом на трассе (подбор бокса, выстрел, мина) сервер должен разослать обновление **всем** клиентам в гонке, а не только автору действия.

Практически: `GameServer` уже хранит всех клиентов лобби в `clients_` (см. [`game_server.h`](../server/game_server.h)) — для этих механик потребуется добавить широковещательную рассылку (`broadcast()` поверх существующего `reply()`, проходящую по всей таблице клиентов) для событий с общей видимостью, тогда как персональные ответы (`AUTH_RESULT`, собственный `STATE_UPDATE`) остаются точечными.
