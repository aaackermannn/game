## 5. Этап 3 — телеметрия и пограничные случаи

1. Использовать `std::chrono::steady_clock`. Передавать метки в микросекундах; в CSV выводить миллисекунды. `sent_at_ms` считать относительно начала серии.
2. Регистрировать запись только после успешной отправки целой UDP-датаграммы. Метку времени брать непосредственно перед отправкой; в документе описать эту точку измерения. Ошибки send логировать отдельно и не выдавать за сетевые потери.
3. Запись содержит sequence, sentAtUs, experiment_id, номер sample, явное состояние и attempts=1. Ограничить активный реестр и историю завершённых записей; задать лимиты и срок хранения. При заполнении не перезаписывать активное измерение, а сообщать ошибку/останавливать серию с диагностикой.
4. Сопоставлять ответ с записью по sequence и исходной clientSendTimeUs; проверять адрес/порт отправителя. Это защищает измерения от случайного PONG, старой серии и повторного использования uint16_t. Не переиспользовать занятый номер. Тестировать переход 65535 → 0 и политику удаления старой истории.
5. Хранить состояния Pending, Received, TimedOut, LateReceived. Одного completed недостаточно: после ExpireOverdue поздний ответ иначе ошибочно станет duplicate_response.
6. Установить timeout=1000 мс. Предлагаемая граница соответствует примеру PDF: RTT <= timeout принимается, RTT > timeout просрочен. Одинаковое правило использовать в приёме и истечении записей; проверить точную границу тестами.

| Исходное состояние / событие | Результат |
|---|---|
| Pending + подходящий PONG в пределах timeout | Received; один RTT и одно обновление метрик |
| Pending + истечение timeout | TimedOut; один timeout |
| Pending + первый PONG после timeout, даже если Expire ещё не вызван | Зафиксировать timeout один раз, затем late_response |
| TimedOut + первый подходящий PONG | LateReceived; late_response; потеря по дедлайну сохраняется |
| Received или LateReceived + повторный PONG | duplicate_response; метрики не меняются |
| Нет соответствующей записи | unknown_response; метрики не меняются |
| Неверный формат/версия/метка/источник | Отбрасывание и диагностический лог; запись не завершается |

RTT считать только как разность двух клиентских меток. Серверные метки не вычитать из клиентских и не использовать для вычисления односторонней задержки. Они нужны для диагностики времени обработки на сервере.

Для каждого принятого вовремя уникального ответа:

- RTT = (clientReceiveUs − savedClientSendUs) / 1000.
- Первое успешное измерение задаёт SRTT; далее SRTT = 0.875 × SRTT + 0.125 × RTT.
- Jitter = среднее абсолютных разностей соседних успешных RTT. Зафиксировать порядок: порядок приёма допустимых ответов, тот же порядок используется в SRTT. При числе RTT меньше 2 jitter считать 0 с явной оговоркой.
- Рассчитывать min/max/mean/median RTT, итоговый SRTT и counts: sent, received вовремя, timeout, late, duplicate, unknown, invalid. При отсутствии успешных RTT min/max/mean/median/SRTT показывать как отсутствующие данные, а не 0.
- Loss Rate = timeout / sent × 100%; при sent=0 не делить на ноль. Поздний ответ не отменяет ранее истёкший дедлайн. После завершения ожидания sent = received вовремя + timeout.

Статистику обнулять между сериями. Поздний пакет из предыдущей серии не должен менять новую серию. Повторной передачи не делать.

Результат этапа: чистая тестируемая модель телеметрии с однозначным учётом состояний.

## 6. Этап 4 — клиент, dedicated-сервер и CSV

Сервер: bind на 27015/UDP по умолчанию, приём датаграммы, фиксация serverReceiveTimeUs, проверка PING, PONG с теми же sequence/clientSendTimeUs и двумя серверными метками. serverSendTimeUs ставить непосредственно перед фактической отправкой. Некорректные пакеты логировать без падения; ошибки сокета отличать от отсутствия входящих данных.

Клиент: CLI с адресом, портом, experiment_id, count, interval_ms, timeout_ms и путём CSV. Проверять диапазон порта, положительные значения count/timeout, диапазон интервала эксперимента 200–1000 мс, ограничения памяти и возможность записи файла. Не начинать серию, если журнал открыть нельзя.

Расписание строить относительно `t0 + i × interval`, используя select/poll или неблокирующий сокет. Приём и истечение записей не должны блокировать очередную отправку на 1000 мс. При отставании расписания фиксировать это в диагностике. После последней отправки дождаться завершения всех активных записей и выдержать документированное дополнительное окно приёма для поздних/повторных ответов; только затем закрывать серию.

CSV сохраняет обязательный префикс колонок:

```text
experiment_id;sample;sequence;sent_at_ms;rtt_ms;srtt_ms;status
```

Предлагается дописать run_id, event_index, received_at_ms, attempts и серверные диагностические метки. Формат чисел — точка независимо от локали, отсутствующие числовые значения — пустые поля. Заголовок писать один раз. Не затирать прошлые эксперименты без явного выбора режима.

Зафиксировать семантику журнала: одна строка received или timeout на отправленное измерение, а late_response/duplicate_response — дополнительные события с тем же ключом. Не считать количество всех строк как N_sent. Неизвестные и некорректные ответы отражать в диагностическом логе; при помещении в CSV не создавать фиктивное отправленное измерение. Скрипт анализа должен учитывать ключ серии/запуска/sample и не удваивать timeout при позднем ответе.

Результат этапа: реальный PING/PONG, постоянный интервал и пригодные для повторного анализа сырые данные.

## 8. Этап 6 — воспроизводимый эксперимент

Обязательный минимум — 6 × 50 = 300 PING. Предлагаемые общие параметры: 50 PING на серию, интервал 500 мс, timeout 1000 мс. Только отправка занимает около 25 секунд на серию; полный запуск дольше из-за ожидания последнего ответа, диагностического окна и настройки профилей. Для более устойчивой оценки 5% потерь можно увеличить число измерений или повторить серии, сохранив отдельные run_id.

| Серия | Требование PDF | Предлагаемая точная конфигурация |
|---|---|---|
| baseline | Без ограничений | Нет искусственных задержек/потерь |
| delay_50 | Дополнительная задержка 50 мс | 50 мс на одном выбранном направлении |
| delay_100 | Дополнительная задержка 100 мс | 100 мс на том же направлении |
| jitter | Флуктуации, например 50–150 мс | Задержка U(50,150) мс на том же направлении |
| loss_5 | Потери 5% | Независимое отбрасывание 5% PONG, без искусственной задержки |
| combined | 100 мс, jitter, 5% потерь | Задержка 100 + U(−50,50) мс и независимые 5% потерь PONG |

Фильтрация только PONG позволяет трактовать добавку RTT однозначно. Если задерживать оба направления на 50 мс, RTT вырастет примерно на 100 мс; если независимо терять по 5% PING и PONG, вероятность отсутствия ответа будет около 9.75%, а не 5%. Эти различия обязательно описать.

Инструмент: по ТЗ Clumsy либо согласованный эмулятор. Перед запуском определить инструмент/версию и проверить применение нужного профиля к выбранному пути, особенно при loopback. Для автоматизации и seed можно предложить программируемый эмулятор с очередью отложенных PONG; его использование согласовать в соответствии с формулировкой задания. Если задержка встроена в сервер, явно обозначить её как искусственную серверную обработку, а не задержку реальной сети. Не блокировать сервер sleep на каждый пакет: использовать очередь сроков отправки, чтобы не создавать непредусмотренное накопление задержки.

В Experiment_Config.md записать ОС, компилятор/IDE и версии, commit, команды сборки/запуска, адрес/порт, размещение клиента/сервера, инструмент и версию, фильтр и направление, все параметры профилей, распределение jitter, вероятность и место потерь, число пакетов, интервал, timeout, окно завершения, дату/время с часовым поясом, seed при наличии. Фиксированный seed воспроизводит решения эмулятора, но не гарантирует побайтово одинаковые RTT из-за ОС и планировщика.

Перед сериями выполнить тесты и короткую проверку связи; затем провести baseline и остальные пять серий. Сохранить исходный CSV и диагностические логи, не подменять измерения ожидаемыми числами. Отдельными контролируемыми проверками вызвать повреждённые, дублирующиеся, неизвестные, переставленные и поздние ответы: шесть сетевых серий сами по себе не гарантируют появления этих событий.

Результат этапа: минимум 300 фактических отправок и полное описание способа их повторения.

## 9. Этап 7 — анализ и оформление

Написать скрипт, который читает CSV, проверяет схему/статусы/повторы, заново рассчитывает статистику по каждой серии и сопоставляет её с итогами клиента. Считать RTT-метрики только по received. Фактические 5% при 50 пробах не обязаны получиться ровно 5%: ожидаемо 2.5 потери в среднем, наблюдаемое количество целое и случайное.

В docs/graphs/ сохранить:

1. Линейные графики RTT по измерениям всех серий с отдельными отметками timeout. Не рисовать timeout как RTT=0 или якобы измеренные 1000 мс.
2. Столбчатое сравнение mean RTT и итогового SRTT по сериям, а loss rate — отдельной панелью/осью в процентах. Не смешивать мс и проценты на одной шкале.
3. Histogram либо box plot RTT для baseline, jitter и combined; в подписях указать число успешных ответов и потери.

В Latency_Report.md включить состав команды, архитектуру, методику, формулы и правила статусов, сводную таблицу sent/received/timeout/late/min/max/mean/median/SRTT/jitter/loss, графики, анализ и выводы. Описать влияние delay/jitter/loss, реакцию SRTT, ограничения размера выборки и среды. Объяснить, почему серверные часы не нужны для RTT и почему поздние/повторные ответы не меняют успешную выборку. Сослаться на конфигурацию и команды повторения.

Результат этапа: графики и выводы полностью выводятся из сохранённого CSV.

## 10. Этап 8 — PR, ревью и готовность к сдаче

1. Проверить сборку и CTest из чистого клона форка, затем короткий запуск клиента/сервера и воспроизводимость анализа CSV.
2. Обновить README: зависимости, сборка, тесты, запуск, профили эксперимента, построение графиков, ссылки на документы.
3. Убедиться, что в коммитах нет build, исполняемых файлов и случайных временных данных; исходные CSV, графики и необходимые логи эксперимента доступны в оговорённых местах.
4. Открыть PR из feature/latency-measurement в фактическую базовую ветку своего форка; связать issues, описать изменения, проверки и результаты.
5. Получить настоящее ревью участника команды и устранить замечания. Самопроверка или комментарий помощника не заменяют это требование. Сохранить обсуждение и подтверждение ревью, затем выполнить merge по процессу команды/преподавателя.
6. Приложить к заданию ссылку на дописанный fork, PR и ревью; при необходимости добавить ссылки на issues и отчёт.

Критерий завершения: всё обязательное из раздела 1 присутствует; сборка и тесты воспроизводятся; шесть серий имеют минимум по 50 отправленных PING; данные и графики согласованы; ошибки/дубли/late проверены; PR и командное ревью существуют фактически.

## 11. Организация времени

Методичка делит работу на два семинара по 90 минут: 15/45/30 минут на проектирование, реализацию и baseline; 20/40/30 минут на конфигурацию, остальные серии и анализ с PR. Это учебное распределение, а не гарантия срока для полного набора пограничных тестов и внешнего ревью.

Порядок зависимостей: fork/issues → контракт → protocol и telemetry с тестами → transport и приложения → baseline → остальные серии → анализ/отчёт → чистая проверка → PR и ревью. Проверки должны появляться вместе с реализацией, а не после получения экспериментальных данных.

Решения, которые нужно зафиксировать перед реализацией: namespace форка; участник команды для ревью; инструмент эмуляции и его допустимость; единая политика дедлайна/истории/CSV. Для составления этого плана доступ к аккаунту, отправка приглашений или развёртывание сервера не требуются.
