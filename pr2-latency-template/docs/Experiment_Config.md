**Задержка встроена в сервер. Это имитация дополнительного времени серверной обработки, а не Clumsy и не физическая сеть.** Использование собственного эмулятора ещё не подтверждено преподавателем; согласование является внешним условием приёмки ТЗ. После согласования либо выбора другого инструмента серии можно повторить скриптом. Административные права и изменения системных сетевых настроек для этого стенда не нужны.

| Серия | Дополнительная задержка PONG | Пропуски |
|---|---|---|
| baseline | 0 мс | Нет |
| delay_50 | 50 мс | Нет |
| delay_100 | 100 мс | Нет |
| jitter | 50+jitter_draw%101 мс: целые 50..150 | Нет |
| loss_5 | 0 мс | loss_draw%10000<500 |
| combined | 100+(jitter_draw%101−50) мс: целые 50..150 | loss_draw%10000<500 |

На каждом PING PRNG делает ровно два шага: первый для loss, второй для jitter даже в baseline. Правила с остатком от деления задают дискретное приближение равномерного распределения; малая modulo bias не устраняется и указана как ограничение. Seed обнуляется между сериями одинаковым значением. Поэтому jitter и combined имеют те же решения задержек, loss_5 и combined — те же решения потерь. Серии предназначены для сравнения факторов и не являются независимыми случайными повторностями.

Пропуски имитируются до отправки PONG. Пакет PING действительно приходит на сервер и виден в логе, соответствующий PONG не посылается. Потери PING не имитируются. При том же seed на 50 пробах пропущены sample 10,16,17 (sequence 9,15,16): 3/50=6%, а не обещанные ровно 5%. В логах сохранён `drop` для каждого PING.

Задержка реализована очередью дедлайнов; сервер не делает sleep на каждый пакет. Фактическое ожидание может превышать заданное из-за дискретности select и планирования Windows. Средний интервал в клиентском расписании стремится к 500 мс, но фактические интервалы в этом запуске были примерно 485..514 мс. Это измерено по CSV; точного real-time расписания обычная ОС не гарантирует. В логах клиента нет schedule_overrun на полный интервал.

## Команды повторения

Из каталога pr2-latency-template, стандартная установка Python и CMake:

```powershell
cmake -S . -B build
cmake --build build --config Release --parallel 4
ctest --test-dir build -C Release --output-on-failure
python -m pip install -r scripts/requirements.txt
python scripts/run_experiments.py --bin-dir build/Release --output-dir docs/repeat_1 --count 50 --interval-ms 500 --timeout-ms 1000 --grace-ms 1200 --seed 20261031 --port 27015
python scripts/analyze_latency.py --docs docs/repeat_1
```

Для Linux использовать `--bin-dir build`. В данной среде использовалась сборка `../build/pr2/Release`, Python из bundled runtime, Catch2 из локального кэша через FETCHCONTENT_SOURCE_DIR_CATCH2. Эти пути влияют на размещение инструментов, а не на формат пакета или формулы. В manifest находятся точные фактические команды.

Runner проверяет свободный порт, ожидает READY, выполняет серии последовательно и сохраняет отдельный run_id, CSV, summary, серверный/клиентский лог. После серии завершает только собственный дочерний сервер. Частичный опыт помечается completed=false; анализ не принимает его за завершённый. Повторный запуск должен использовать новый output-dir. Сохранённый git_head — состояние родительского Loop до коммита реализации; фактически измеренная версия дополнительно однозначно зафиксирована SHA256 всех исходников и бинарников. После измерений код вычислений и транспорта не менялся.
